You can use https://docs.micronaut.io/latest/guide/index.html#distributedConfiguration[Distributed Configuration] with Google Cloud Parameter Manager by importing specific parameters through `micronaut.config.import`.

This is the preferred approach for new applications because it avoids bootstrap-specific wiring and makes each imported parameter explicit.

IMPORTANT: Make sure you have configured credentials following the <<setup, Setting up GCP>> section, and that the configured identity can read the target parameters. If you need more information, see the official link:https://docs.cloud.google.com/secret-manager/parameter-manager/docs/access-control[Parameter Manager access control] documentation.

== Importing a configuration parameter

Store a configuration payload such as YAML, JSON, or properties in a Parameter Manager parameter. Parameter Manager does not keep file extensions, so the importer either uses the configured `format` or defaults to YAML-style parsing for extensionless parameters.

[source,yaml]
----
micronaut:
  config:
    import: gcp-parameter-manager://application?project-id=my-gcp-project&version=1
----

The importer renders the parameter version at startup and publishes it as a Micronaut property source. See <<parameterManagerParametersResolution,Parameters Resolution>> below for how secret references inside a parameter are handled.

When you use the scalar connection-string form, you can pass additional importer options as query parameters:

[source]
----
micronaut.config.import=gcp-parameter-manager://application?project-id=my-gcp-project&version=1&credentials-location=credentials-file-path
----

In that form, `credentials-location` maps directly to the importer option of the same name. If you need `encoded-key`, prefer the structured import form below so the Base64 value does not need URI escaping. If neither credential option is supplied, the importer falls back to Application Default Credentials.

== Structured import declarations

If you need to pass extra options such as credentials, project id, or regional location, use the structured import form:

[source,yaml]
----
micronaut:
  config:
    import:
      provider: gcp-parameter-manager
      path: application
      project-id: my-gcp-project
      version: 1
      format: yml
----

Supported importer options are:

|===
|Option |Description
|`path` |The parameter name to import
|`project-id` |The Google Cloud project containing the parameter
|`version` |The parameter version to import. Required; Parameter Manager does not support `latest`
|`format` |Explicit payload format such as `yml`, `yaml`, `json`, or `properties`
|`location` |Regional Parameter Manager location for regional parameters
|`credentials-location` |Path to a service account credentials file used only for this import
|`encoded-key` |Base64 encoded service account credentials used only for this import
|`optional` |Marks the import as optional
|===

When `credentials-location` and `encoded-key` are both absent, the importer falls back to Google Application Default Credentials, using the same resolution order described in the <<setup, Setting up GCP>> section.

== Retry options

`gcp-parameter-manager` imports also support the standard retry options provided by `RetryablePropertySourceImporter`. These options work with both scalar connection-string imports and structured import declarations.

|===
|Option |Description
|`retry-attempts` |Maximum number of attempts
|`retry-count` |Alias for `retry-attempts`
|`retry-delay` |Delay between attempts
|`retry-max-delay` |Maximum overall retry delay
|`retry-multiplier` |Delay multiplier applied between attempts
|`retry-jitter` |Jitter factor from `0.0` to `1.0`
|===

Example using scalar connection-string form:

[source,yaml]
----
micronaut:
  config:
    import: gcp-parameter-manager://application?project-id=my-gcp-project&version=1&retry-attempts=5&retry-delay=1s&retry-multiplier=1.5
----

Example using structured form:

[source,yaml]
----
micronaut:
  config:
    import:
      provider: gcp-parameter-manager
      path: application
      project-id: my-gcp-project
      version: 1
      retry-attempts: 5
      retry-delay: 1s
      retry-max-delay: 30s
----

== Regional imports

To comply with data residency requirements, you can point the importer at a regional parameter by setting `location` in the import declaration:

[source,yaml]
----
micronaut:
  config:
    import:
      provider: gcp-parameter-manager
      path: application
      project-id: my-gcp-project
      version: 1
      location: us-central1
----

== Parameters Resolution

The framework uses the link:https://docs.cloud.google.com/secret-manager/parameter-manager/docs/render-parameter-version[render functionality] when reading parameters. This allows parameter versions to reference secrets stored in Google Cloud Secret Manager.

IMPORTANT: If a parameter references a Secret Manager secret, the specific parameter must also be granted the Secret Manager Secret Accessor role for that secret. Refer to the official link:https://docs.cloud.google.com/secret-manager/parameter-manager/docs/reference-secrets-in-parameter[Reference Secrets in Parameter] guide for more details.

Because imports are required by default, a parameter whose secret reference cannot be resolved (missing secret, or missing `roles/secretmanager.secretAccessor` on it) fails application startup rather than loading with a missing property. Add `optional: true` to the import declaration if you want startup to continue without it instead.

== Legacy bootstrap integration

The older bootstrap/config-client based integration remains available for existing applications. Unlike Secret Manager, it has no default parameter name resolution -- you must explicitly whitelist every parameter through `custom-configs` or `keys`, each given as a `<parameter-name>/<parameter-version>` pair.

For new development, prefer `micronaut.config.import`. Use the bootstrap configuration path only when you need this legacy resolution behavior.

.bootstrap configuration
[configuration]
----
micronaut:
  application:
    name: sample-app
  config-client:
    enabled: true
----

IMPORTANT: The service account used by your application must have permission to read parameters. See the official link:https://docs.cloud.google.com/secret-manager/parameter-manager/docs/access-control[Parameter Manager access control] documentation.

=== Regional parameters (legacy)

Set `gcp.parameter-manager.location` to use the bootstrap client against a regional endpoint:

[configuration]
----
gcp:
  parameter-manager:
    location: us-east1
----

=== Custom configuration files

`custom-configs` loads a parameter's content as a configuration file (`yaml`, `json`, or `properties`), merging its keys directly into the environment:

[configuration]
----
gcp:
  parameter-manager:
    custom-configs:
      - my-first-config/v1
      - my-second-config/v1
----

TIP: Entries under `custom-configs` must be valid configuration files, not individual key/value entries.

=== Key/value parameters

`keys` loads a parameter's raw content as a single string value, rather than parsing it as a config file -- useful for a parameter that stores something like a `DB_PASSWORD`:

[configuration]
----
gcp:
  parameter-manager:
    keys:
      - DB_PASSWORD/newVersion
      - dbUser/otherVersion
----

Keys are exposed in the environment under a `pm.` prefix, converted to dotted-lowercase form:

|===
|Parameter name/version |Resolved property
|`DB_PASSWORD/newVersion` |`pm.db.password`
|`dbUser/otherVersion` |`pm.db.user`
|===

== Parameter Versioning

Google Cloud Parameter Manager supports link:https://docs.cloud.google.com/secret-manager/parameter-manager/docs/list-parameter-versions[parameter versioning]. Unlike Secret Manager, it does not support `latest` as a version -- every import, whether through `micronaut.config.import` or the legacy bootstrap path, must specify an explicit version.
